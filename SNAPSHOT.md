# SNAPSHOT

## Project

SignalForge builds SignalRGB lighting effects from images. An effect is a self-contained HTML file whose engine composites layers onto a 320x200 canvas; SignalRGB samples that canvas under every LED. Nothing else on the market makes effects from photos — the existing community tools only do geometric shapes.

## Decisions made

- **Video inside a SignalRGB effect is impossible.** Measured on the real host: `<video>` exists but has no `play()`, so the script aborts and the render loop never starts. Not the file size, not the codec — both an embedded data URI and a sibling file fail identically. Any future video feature must go through an image sequence. Evidence: `C:\Users\Max\claud\signalforge\docs\erkenntnisse-signalrgb-motor.md`.
- **An effect cannot receive live data.** SignalRGB serves effects from its own HTTPS origin (`signalrgbmarketplace.pages.dev`), so a sibling file is out of origin and a localhost server is mixed content, blocked before CORS is consulted. Everything an effect knows must be baked in at export time. This closes off wallpaper synchronisation. Same document.
- **`ctx.filter` is absent on the host.** Brightness and colour are computed by hand over the pixel buffer, in one shared pass that is skipped entirely when neutral. No layer type may use `ctx.filter` at render time.
- **The preview loads the same `dist/engine.bundle.js` the export embeds.** This is what makes `test/export/parity.test.js` meaningful and must not be replaced by importing engine sources directly in the app.
- **Layers carry `motions` (an array), not `motion`.** `normalizeDocument` still converts the old singular form so previously exported effects and saved projects load. Render order is fixed **`spin → drift → warp → pulse → breathe`**, not list order, so the result does not depend on how the user sorted the list. Spin comes first because it is the only motion that changes the GEOMETRY the others then work on (it is folded into the angle before a colour stop is placed); pulse and breathe are both factors on `globalAlpha` and therefore commute, but the order is written down anyway. The full statement lives in `src/engine/layers/gradient.js`.
- **Not every motion is offered on every layer type** (`motionKindsFor`, `src/engine/document.js`), and the rule is "can it be SEEN to do this", not taste. A solid colour gets `breathe` and `pulse` only — drift, warp and spin all move pixels, and on a uniform field every pixel they move is replaced by one of the same colour. A picture gets everything but `spin`: a 320x200 rectangle turned about its centre only stays covered if the picture is zoomed to the canvas diagonal first, which throws away 72 % of the crop the user chose. A gradient gets all six.
- **A gradient has five shapes: `linear`, `radial`, `conic`, `stripes`, `waves`** — all values of one `shape` field, for the reasons already recorded under GRADIENT_SHAPES. The three that repeat are steered by a `bands` field (whole repeats, clamped 1..24). `bands` and `angle` are stored on every gradient and offered by the exported effect whatever the shape, because the Shape dropdown can be switched from SignalRGB's own panel; the settings column in the app hides each of them where it provably does nothing (no angle on a radial, no band count on linear/radial, no stop POSITIONS on stripes).
- **The conic is built out of wedges into a cached offscreen canvas and painted through a rotation, NOT with `createConicGradient`.** That API needs Chrome 92 and the host's real version is unknown — its user agent claims 85 and is a known lie. Wedges (`moveTo`/`arc`/`fill`) have been in canvas since it existed. Measured cost of the whole thing: 0.005 ms/frame still, 0.34 ms with a spin and a warp on it at once. Do not "simplify" this to `createConicGradient` without measuring on Max' own SignalRGB first.
- **An own lighting application on top of OpenRGB was considered and deliberately deferred**, at Max' decision on 2026-08-09: he wants a finished effect builder in reasonable time first. Findings and effort estimate are preserved in section 9b of the specification. Do not reopen it unless Max raises it.
- **Licence GPLv3, code and commits in English, docs in German, interface bilingual.** Name SignalForge chosen by Max after being told it sits close to the SignalRGB trademark.

## Since build plan 2 (11./12.08.2026, second wave — Max' feedback list)

Max reported: motions dead in SignalRGB, brightness capped, tempo too slow, white icon corners, the left column pointless, no effect library, too few shapes, no cover images, and later: moving colour backgrounds. All closed:

- **The motion-in-SignalRGB bug had TWO silent causes**, both fixed: a host control value missing every option deleted all motions (strict equality — now a resolve chain), and the export's frame loop wedged forever on a frozen rAF timestamp — SignalRGB's own binary proves stalls are a designed-for condition there (`"Still stale after {} frames"`). The export now carries a second, independent interval loop; a double-count of time between the two loops was caught in review and fixed.
- **Brightness 0–200** (100 = exactly before, mid-slider), **tempo ceiling** 10.5 s → 1.5 s per breathe at 100 (anchor at 15 bit-identical), **icon corners transparent**.
- **The effect library:** the gallery strip has two tabs — starting tiles and the effects folder as a shelf. **Every exported effect carries its own document** (`<script id="sf-document" type="application/json">`) and is reopenable; foreign HTML is parsed with the same validator as project files, 4 MB bound, decoy-block refusal, prototype-pollution safe.
- **Shapes and motions:** gradient shapes `conic`/`stripes`/`waves` + `bands`, motions `spin`/`pulse`; a **shape layer** (circle/ring/star/heart on transparent ground); **`trail`** (afterglow) + **`hueShift`/`hueCycle`** (true Rodrigues hue rotation) document-wide.
- **A particle layer** — rain/rise/drift/snow, 1–400, closed-form `x(i,t)` from a seeded `triple32` hash (no `Math.random`, no per-particle state), so parity survives, including 30-frame **sequence parity** (trail makes frames history-dependent; parity is now defined from frame 0 for trail documents).
- **A background slot** (`layers[0]` background, last = foreground, id-based addressing in `src/engine/slots.js`) — moving colour backgrounds under particles/shapes/contain-images, exported as `bg*` controls.
- **The wake composes over the background**: a second transparent wake buffer for the foreground only; the background stays live, tails fade toward its current colour. Chromium's compositor cannot do the attenuation (stalls at 25/255 — measured); a JS loop does it. The particle tile ships the corpus-proven geometry (50 drops, size 10, speed 16, trail 45) so one press gives comet tails.
- The render order is `spin → drift → warp → pulse → breathe`, stated identically in every layer file. `docs/effekt-inventur.md` maps 31 real SignalRGB effects to our vocabulary — read it before adding effect features.

- **Every export now writes its own tile picture.** `<Name>.png` beside `<Name>.html`, 512 x 288, frame zero of that very document through the real engine bundle — the app's export button and `bin/sfexport.js` both, through one shared renderer (`src/main/cover-image.js`). The mechanism is proven, not assumed: Max saw the probe tile in his own SignalRGB list on 11.08.2026 (`docs/messung-titelbilder.md`). Rendered in a hidden window in the main process; the renderer never sees a path. If the picture cannot be drawn or written, the effect is still exported and the reason is said out loud (`export.noCover`).

Two facts worth keeping: `requestAnimationFrame` does not tick in a hidden window (drive frames from outside), and a hidden window needs **two** `capturePage()` calls or the canvas comes out blank.

**And no leftover processes.** Three orphaned `electron.exe` from harness runs were found six hours old on Max' machine. **An Electron main process does not die of an unhandled promise rejection** — it prints a warning and runs on forever with its window open, which is measurable and was measured. So every Electron entry goes through `runHarness`/`guardHarness` in `test/harness/driver.js` (watchdog, `uncaughtException` + `unhandledRejection`, and a `finally` that always leaves) and every spawn goes through `runElectron` in `test/harness/spawn-electron.js` (which always kills). **Rules for anyone adding a harness:** use those two, never write `app.whenReady().then(...)` bare, never `app.quit()` — it is a request a close handler may refuse and it carries no exit code — and keep a harness's own watchdog *below* its caller's timeout. Never make a harness exit 0 unconditionally to "fix" a leak: that turns a red run green. Details and the falsifiability evidence: `.superpowers/sdd/harness-cleanup-report.md`.
